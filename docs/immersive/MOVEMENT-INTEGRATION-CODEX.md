# Courtyard movement integration handoff

The controller is an isolated building block; Walk remains disabled and guided selection is unchanged. Do not enable Walk until the steps below and the route/device checks pass.

- Import `CourtyardController` and `MovementInput` from the courtyard directory. Create the controller once with the validated manifest; handle a rejected `create()` by retaining guided mode and showing an accessible failure message. Dispose it on scene unload, manifest replacement, failed setup, or context loss. Avoid recreating on resize.
- Own the camera in exactly one mode: unmount/disable `GuidedCamera` in Walk mode, use `controller.eye` for the walking camera position, and restore guided ownership on exit. `advance(deltaSeconds, input.vector(), yaw)` clamps catch-up and runs 60 Hz collision steps; yaw zero faces -Z. Keep pitch in the view layer. Revalidate the spawn before allowing entry.
- Wire keydown/keyup through `MovementInput`; call `clear()` on window blur, visibility loss, pointer-lock loss, modal opening, leaving Walk, and focus entering editable or dialog content. Use `isEditableTarget` for focus checks and do not hijack controls within the UI. Ask for pointer lock only in direct response to a click, handle rejection, and release on Escape. Provide accessible DOM movement/interaction alternatives and touch input mapped to the same normalized axes.
- On an intentional interaction action, call `nearestVisible()` then pass a non-null ID to the existing `onSelect`; no target means no selection. This is proximity and collider line-of-sight, not a view-direction reticle. Existing guided pointer/DOM interactions remain separate. Review each proxy: the object-named collider is excluded for its own ray and other proxies can occlude it.
- `recover()` resets to the manifest spawn; automatic recovery triggers below the lower world bound. Expose an accessible recovery control. Input and physics do not implement gamepad, XR, touch controls, pointer lock, modal state or a React component.
- Verify the complete spawn → offer → intake → bridge → memo → reverse route, rail/counter collisions, camera clipping, object reachability and occlusion, focused inputs, blur/escape, no-WebGL and physics-load failures, resize, mobile controls, and real browser/device performance. Record route video and collider debug screenshot. Current tests are focused physics tests, not route or browser acceptance.

## Integration update — 3 November 2026

Walk is now wired in Courtyard.tsx and World.tsx. It starts from the manifest entrance, owns the camera while active, clears keyboard input on blur and pointer-lock loss, and disposes its physics world on exit. Named buttons provide turning, stepping, inspection and recovery; a Guided object list is available without canvas selection. The route through Offer, Intake, Bridge and Memo and back passed against the actual collider manifest in Vitest, along with focused collision, input and interaction checks (5 tests total). TypeScript passed.

Browser acceptance is outstanding. The in-app browser displayed the loading shell and Guided object list, but the 3D scene did not become ready during the attempt; the browser automation timed out and Vite logged WebGL shader validation errors. No browser route, object selection, pointer lock, device/touch, screenshot or performance acceptance is claimed. Inspect nearest uses proximity and line of sight, not a gaze reticle. Gamepad and XR remain unimplemented. The button-step controls were not usability tested.

## Rapier lifecycle regression — 3 November 2026

The controller's bare import currently resolves to Rapier 0.12.0 through @types/three; @react-three/rapier has a separate nested 0.19.2. An isolated test starting two controller creations concurrently, disposing one, then advancing the other reproduced the historical unsafe Rust aliasing error at computeColliderMovement. Sharing one initialization promise (and permitting retry after initialization rejection) makes that test pass through 20 lifecycle rounds with movement, inspection and recovery. Typecheck and the full 37-file / 242-test suite pass. React StrictMode may cause overlapping setups; the historical incident's exact trigger is not established. No dependency was installed or changed; browser testing after the fix remains open.

## Browser acceptance, 4 November 2026

Superseded notes above: the "no visible change" observation and the Edge WebGL failures were test-setup problems (a `--disable-gpu` launch, then a machine out of memory). Walk was checked in Edge with the real GPU; results are in `implementation-status.md`.

Changes from the design above: looking is by dragging, not pointer lock, so the cursor stays free to click objects and there is no lock state to lose. On-screen buttons hold like keys. Pressing a place or a far object walks there along `route.ts`; any movement key takes control back. Keys are read on the window except in editable targets and dialogs, so focus on a panel button does not stop walking. Rapier is a direct dependency at 0.19.2 (`hit.timeOfImpact`, no `updateSceneQueries`) and loads only when Walk starts.
